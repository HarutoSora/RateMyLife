# Rate My Life

## Product

Rate My Life is a social mobile application where users:

- Create anonymous lifestyle profiles.
- Upload profile and lifestyle photos.
- Enter information about their lives (income, career, education, habits, etc.).
- Receive an algorithmic Life Score.
- Receive ratings from other users.
- Rate other people's lives.
- Discover anonymous profiles.
- Compare their Life Score with community perception.
- Share their results.

The product is entertainment / social comparison.

**The Life Score must never be presented as a measurement of someone's human worth.**

## Technology

This reflects what is actually in the repository — keep it accurate as the stack evolves.

- Flutter 3.47 (Dart 3.13, `sdk: ">=3.4.0 <4.0.0"`)
- State management: Riverpod (`flutter_riverpod`), via a single `ChangeNotifierProvider<AppController>` in `lib/presentation/state/app_state.dart`
- Material 3 (`useMaterial3: true`), dark, "neon arcade" brand theme in `lib/core/theme/` (see Brand identity below)
- Fonts: `google_fonts` (Baloo 2 for display/headings, Nunito for body/UI) — fetched at runtime and cached by the package; see the caveat in `docs/DEVELOPMENT_PLAN.md` if text renders in a fallback font in an offline/sandboxed environment.
- Backend: Firebase — `firebase_core`, `firebase_auth` (anonymous sign-in only, no name/email collected), `cloud_firestore`, `firebase_storage`. Project: `rate-my-life-2c381`; config in `lib/firebase_options.dart` + `android/app/google-services.json` (generated by `flutterfire configure`, not hand-edited). Security rules live in `firestore.rules` / `storage.rules` at the repo root and deploy via `firebase deploy --only firestore:rules` / `--only storage`.
- Data access is via `Local*Repository` (SharedPreferences/`path_provider`, used when signed out) or `Remote*Repository` (Firestore/Storage, used once signed in) implementations of the same abstract repository interfaces in `lib/data/repositories/repositories.dart` — `RepositoryBundle`/`repositoryBundleProvider` picks which set based on `FirebaseAuth.instance.currentUser`. Every repository now has both. See each `Remote*Repository`'s doc comment for its specific privacy model (e.g. ratings are anonymous even from the profile owner; income/savings are owner-only unless the profile's privacy flags opt in; battles/XP/coins/achievements/challenges are private device-only logs nobody else ever reads).
- Testing Firestore-backed repositories: use `fake_cloud_firestore` + `firebase_auth_mocks` (dev dependencies) to inject a fake `FirebaseFirestore`/`FirebaseAuth` into a `Remote*Repository`'s constructor — see `test/remote_battle_repository_test.dart` / `test/remote_progression_repositories_test.dart` for the pattern. This does not validate security rules (the fake has none); a rules change should get a quick unauthenticated `curl` sanity check against the deployed rules instead of a full manual run.
- Photos: `image_picker`, uploaded to Firebase Storage under `profile_photos/{uid}/` when signed in (falls back to local app-documents storage when signed out); `ProfileImage` renders `http(s)://` paths via `Image.network`, local paths via `Image.file`.
- IDs: `uuid` for local-only installs; a signed-in profile's id is its Firebase Auth UID instead (see `ProfileRepository.newProfileId`), so the same person's data lines up across devices.
- Android-first, iOS-compatible (platform folders exist for both; a `web/` target was also added for local visual QA — see Development scripts)
- `tools/flutter/` is a vendored Flutter SDK checkout used for local tooling — it is not part of the app and is excluded from `flutter analyze` (see `analysis_options.yaml`). `.flutter_scaffold/` is a stale, unused `flutter create` scaffold left over from project setup — also excluded, do not build on it.

## Brand identity

The app uses a "neon arcade" visual identity: deep purple/navy backgrounds, violet glow, and gold/pink/blue gradient CTAs, driven by the app icon at `assets/branding/logo.png`. Reference: `docs/DESIGN_SYSTEM.md`.

- Colors: `lib/core/theme/app_colors.dart` (`AppColors`) — grounds, text, brand accents (`purple`, `pink`, `gold`, `blue`, `green`, `neonRed`), and gradients (`goldGradient`, `purpleGradient`, `pinkGradient`, `blueGradient`, `greenGradient`, `neonRedGradient`, `heroGlow`).
- Type: `lib/core/theme/app_typography.dart` (`AppTypography`) — `hero`/`title`/`heading` in Baloo 2, `body`/`bodyMuted`/`caption`/`button`/`eyebrow` in Nunito.
- Radius: `lib/core/theme/app_radius.dart` (`AppRadius`) — `sm`/`md`/`lg`/`pill`, rounder than a typical utility app.
- Brand components: `lib/presentation/widgets/brand_widgets.dart` — `AppLogo`, `GradientButton` (full-width gradient pill CTA — use for primary actions, one of the four gradients above), `ScoreBadge` (hexagonal crown-and-score hero, used on Score/Home).
- Most existing widgets (`AppCard`, `MetricPill`, `ScoreTile`, chips, inputs, bottom nav) re-theme automatically through `AppTheme`/`AppColors` tokens — don't hand-roll new colors on top of them.
- As of this pass, Splash, Onboarding, and Home (quick-action buttons) and the Score screen hero use the new brand components directly. Discover, Leaderboard, Profile, Photo Manager, and the Profile Wizard are re-themed via tokens (new colors/fonts/radii) but haven't had a bespoke layout pass yet — do that with the `flutter-ui` skill before considering them "polished" to this identity.
- Not yet implemented: a floating center "+" button in the bottom nav (seen in the reference mockup) — the nav is still a plain `BottomNavigationBar`, themed but not restructured.

## Architecture (as implemented)

```
lib/
  core/theme/            AppTheme, AppColors, AppTypography, AppSpacing, AppRadius
  data/
    models/models.dart       All data models (UserProfile, LifeScore, Rating, Report, etc.)
    repositories/repositories.dart   Abstract repositories + Local* implementations + RepositoryBundle
    mock/mock_profiles.dart  Seed data for the discovery/leaderboard feeds
  domain/
    scoring/life_score_service.dart   LifeScoreService (pure calculation, country benchmarks)
    services/   ProfileService, RatingService, PhotoService, ModerationService
  presentation/
    state/app_state.dart     AppController (ChangeNotifier) — the single source of app state
    screens/screens.dart     All screens
    widgets/widgets.dart     All reusable widgets
```

`models.dart`, `screens.dart`, and `widgets.dart` are large barrel-style files (800-1500 lines) containing many classes. This is existing technical debt, not a target — see `docs/DEVELOPMENT_PLAN.md`. Do not add new screens/widgets/models into these monoliths by default; when a file is doing double duty and you are touching it anyway, splitting it into `lib/presentation/screens/<feature>/` etc. is reasonable, but do not do a drive-by split of a file you weren't asked to change.

## Permanent development rules

### Architecture
- Keep presentation, business logic, and data access separated.
- Do not put business logic directly inside widgets.
- Do not create giant files. Prefer splitting by feature when adding substantial new code.
- Prefer reusable widgets over copy-pasted layout.
- Avoid duplicated business logic — put it in a service under `lib/domain/services/`.
- Use repositories (`lib/data/repositories/`) for all data access; nothing else should touch `SharedPreferences`/`dart:io` directly.
- Keep models independent from UI (no Flutter imports in `lib/data/models/`).
- Do not introduce unnecessary dependencies.
- Do not rewrite working architecture without a concrete reason.

### Flutter
- Follow Flutter conventions; maintain null safety.
- Avoid unnecessary rebuilds (scope `ref.watch` narrowly, prefer `Consumer`/`select` over rebuilding whole screens).
- Avoid hard-coded screen dimensions; support different phone sizes; prevent overflow errors.
- Use accessible touch targets (48dp minimum, already the button default in `AppTheme`).
- Respect system text scaling where practical.
- Use Material 3 consistently.

### UI
The app should feel like a modern consumer social app, not a dashboard.

Avoid: corporate dashboard aesthetics, generic CRUD layouts, excessive gradients, random colors, inconsistent spacing/typography, huge walls of text.

Use: the tokens in `lib/core/theme/` (`AppColors`, `AppTypography`, `AppSpacing`, `AppRadius`), reusable components from `widgets.dart` and `brand_widgets.dart`, strong visual hierarchy, smooth but restrained animations, dark-first design.

### Product
Every feature must support the core loop:

```
Create Life -> Get Score -> Publish -> People Discover -> People Rate ->
Receive Rating -> Compare -> Share -> More People Join
```

Do not add features simply because they are technically interesting.

## Social safety rules (non-negotiable)

- Users cannot rate themselves (`RatingService.upsertRating` already enforces this — do not remove).
- One active rating per user per profile (`upsertRating` upserts by `raterId` + `profileId`).
- Users can update or remove their own rating.
- Users can block other users; blocked profiles must disappear from discovery/leaderboard/rating feeds.
- Users can report profiles/photos; reporting also blocks (see `AppController.reportProfile`).
- Users can delete their own photos and their whole profile.
- Private fields (income, savings, etc., per `ProfilePrivacy`) must never leak into public/discover views regardless of screen. For signed-in users this is enforced server-side by `firestore.rules` (separate `private/income` / `private/savings` / `private/financeExtra` subdocuments, not just client-side filtering of one document) — any new private field must follow the same split-document pattern, not just a client-side `if` check.
- Never expose the identity of anonymous raters by default. For signed-in users this is enforced server-side: `firestore.rules` denies reading a `ratings/{raterId}_{profileId}` document to anyone but the rater themselves, including the profile owner — public rating averages come only from the `ratingSummary` aggregate on the profile document, updated via an incremental transaction in `RemoteRatingRepository` that never reads another user's individual rating.

## Development workflow

When asked to implement a feature:

1. **Inspect** the relevant existing code. Do not assume architecture.
2. **Plan** — give a short implementation plan, not a giant explanation.
3. **Implement** the feature completely. Do not leave core functionality unfinished or add placeholder screens.
4. **Test** — run `flutter analyze` and relevant `flutter test` targets (or `scripts\analyze.bat` / `scripts\test.bat`).
5. **Fix** actual errors. Do not refactor unrelated code while doing this.
6. **Review** against the relevant skill: UI -> `flutter-ui`, architecture -> `flutter-architecture`, tests -> `flutter-testing`, performance -> `flutter-performance`, social features -> `social-safety`, product flows -> `product-review`.
7. **Report** concisely: Implemented / Changed / Tests / Issues / Next recommended step. If there's anything an automated test can't cover (real device rendering, a visual/UX judgment call, a platform-specific flow), end with a short **"What to check"** list of concrete manual steps for the user to run themselves — do not drive the emulator/browser yourself for this unless the user explicitly asks you to.

## Working rules

- Do not rewrite working code unnecessarily.
- Do not create giant files.
- Every button must work. Never leave placeholder screens for core functionality.
- Do not add dependencies unless necessary.
- Keep the application fast on low/mid-range Android phones — see `flutter-performance` skill, especially around photo feeds.
- Do not over-engineer: this is an MVP. No microservices, no complex backend, no premature optimization, no excessive abstraction or DI frameworks.
- Do not refactor unrelated code while implementing a feature.
- Make reasonable engineering decisions on obvious implementation details without asking. Only ask when a decision materially changes product behavior, privacy, security, architecture, cost, or UX.
- For every new user-facing action (submit, edit, delete, vote, react, upload, etc.), add or extend an automated test (`test/`) that exercises it end-to-end against fake/local repositories, alongside the implementation. Prefer this as the primary way to verify behavior — it is far cheaper than manual UI driving.
- Do not drive the Android emulator (ADB) or a browser yourself to verify a feature unless the user explicitly asks you to. Default instead to: write/run automated tests, then give the user a short, concrete "What to check" list so they can verify manually themselves. This applies to anything an automated test can't cover — real device rendering, Firestore security rules, physical upload/download, visual/UX judgment calls.
