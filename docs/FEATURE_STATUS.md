| Audio calls | ✅ | **Done 2026-08-24 — user-requested follow-up to Direct messages.** 1:1 audio calling via `flutter_webrtc`, signaled through Firestore (`calls/{id}` doc + `callerCandidates`/`calleeCandidates` ICE subcollections). Explicitly narrower than a full VoIP product, flagged to the user up front: **STUN-only, no TURN relay** (a TURN service is paid and wasn't approved — connection works on Wi-Fi/most NATs but can fail on restrictive carrier networks); **foreground-only**, no CallKit-style background service, so a call drops if the app leaves the foreground. Two safety gates added beyond the literal ask, per the `social-safety` skill's stricter bar for live audio vs. text: a call requires an existing message conversation first (`CallService.assertCanCall`), and a separate `allowCalls` privacy toggle (default on, in Privacy Settings) independent of `allowMessages`. `CallSession`/`CallStatus` model, `CallService` (pure eligibility rules, mirrors `MessageService`), `CallRepository`/`LocalCallRepository`/`RemoteCallRepository` (Firestore signaling + WebRTC peer-connection lifecycle). Full-screen `CallScreen` (ringing both directions, active call with mute/duration timer) rendered by `AppShell` in place of the tabbed UI whenever a call is live, so an incoming call interrupts whatever screen is open — driven by a live Firestore listener (`AppController.currentCall`), the one deliberate exception to this app's usual load-once-and-refresh state pattern, since an incoming call can't wait for a manual refresh. Call button on `ConversationScreen`'s app bar, shown only once a thread exists and both sides allow calls. Same query-alignment lesson from the messages bug applied proactively: the `calls` Firestore rule checks `participants` directly to match the `array-contains` query. Firestore rules deployed. Anonymity/moderation not extended to calls: no report/block-during-call UI beyond the existing block flow, since a call can only happen with someone already message-reachable (already reportable/blockable there). 11 new tests (`call_service_test.dart`, an integration group in `xp_progression_integration_test.dart` covering the eligibility gates) — all passing. **What to check manually** (needs two real devices/accounts, not automatable): place a call and confirm audio flows both ways, confirm mute works, confirm ending from either side ends it for both, confirm the ringing screen appears without the callee doing anything. **Update 2026-08-24 — verified live on two real emulator instances, found and fixed two real bugs the single-device testing this session had never exercised:**
1. **The incoming/outgoing call screen never appeared unless you navigated back.** `AppShell` swapped to `CallScreen` inside its own `build()`, but `AppShell` is frequently *not* the topmost route (e.g. starting a call from inside `ConversationScreen`, which is pushed on top of it) — the swap happened invisibly underneath the active route. Fixed by moving the takeover into `MaterialApp`'s `builder` in `main.dart` (wraps every route the Navigator ever shows, so it's route-independent) and deleting the old in-`AppShell` conditional.
2. **A message could get silently rejected by Firestore's security rules for a profile that predates the `allowMessages`/`allowCalls` fields.** Found via a real two-account test: one long-lived test account's profile (created earlier in this session, before those fields existed in the schema) was missing them entirely in its stored Firestore document — `saveCurrentProfile`'s merge-only writes never backfill fields a doc never had. The client masks this with `ProfilePrivacy.fromJson`'s `?? true` default (so Privacy Settings *looked* like everything was on), but `messagesAllowed`/`callsAllowed` in `firestore.rules` did a raw `.allowMessages == true` dot-access — Firestore rules error out (denying the whole request) on a genuinely missing map key rather than treating it as null, so anyone trying to message or call that profile got silently denied. Fixed by switching both to `.get('allowMessages', true)` / `.get('allowCalls', true)` — the safe accessor, defaulting exactly the way the client already does, no data migration needed. This is a real, general lesson for any future privacy field: a security rule must use the safe-default accessor from day one, or every profile that existed before the field shipped silently breaks under it. Not part of the spec above — a separate, explicitly-requested pivot from local-only
`SharedPreferences` storage to a real synced backend, so real installs on different devices
can actually see and interact with each other (the whole point of "linking users").

Architecture: `RepositoryBundle`/`repositoryBundleProvider` picks `Local*` or `Remote*` for
every repository based on `FirebaseAuth.instance.currentUser` — the switch is transparent to
`AppController` and every screen, since both implementations satisfy the same abstract
interfaces that were already in place before this migration.

## Why the rest isn't "done in one pass"

This spec is ~15 phases covering new models, services, repositories, screens, and a moderation
surface (comments) that touches privacy/safety directly. Building all of it in one sitting without
verification between phases is exactly what the spec's own Section 47 ("Do not move to the next
phase if the current phase is broken") warns against. This document will be updated as each
subsequent phase lands.
