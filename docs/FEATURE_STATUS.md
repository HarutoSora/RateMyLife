| Coins/XP/score hardening | 🟡 | **Done 2026-08-26 — user-requested: "harden the entire app... where users can hack scores or coins."** Found the coin/XP economy was almost entirely client-trusted: `xpTransactions`/`coinTransactions` — the ledger `Wallet`/`LevelInfo` sum from — validated only that a write's `profileId` matched the writer, never the `amount`, so any signed-in device could write a transaction doc with `amount: 999999999` directly (bypassing the app's UI and `ProgressionService.xpRewards`/`RewardService.coinRewards` entirely) and inflate its own balance/XP without limit; separately, a nuke attacker's cross-profile `score` update had no bound on the new value at all, so a stranger could set another user's `score.overall` to anything, not just apply real `-5`-sized damage. Added `validXpAmount`/`validCoinAmount` (exact-match against the real reward tables — a genuine, disclosed maintenance cost: the tables now live in two places, Dart and rules, and must be kept in sync), `validScoreBounds` (every `LifeScore` category must stay 0-100, the same range `LifeScoreService._clamp` always guarantees), and a tightened nuke-branch bound (`nukesSurvived` must increase by exactly 1, exactly one `nukeDamage` category may change, and `score.overall` may only move within a single nuke's real impact). Also bounded the **owner's own** profile writes (`ownerProfileUpdateIsSafe`): a single write can't increase `coins`/`xp` beyond the largest real single-grant amount (15000 / 1000), and `score` must stay in-bounds — this doesn't require a matching transaction to exist (Firestore rules can't correlate that across documents without a Cloud Function), but it closes the one-shot "set my balance to 999999999" exploit. All new rule logic verified against a real, temporarily-started Firestore emulator via `@firebase/rules-unit-testing` (17 cases: legit rewards succeed, forged amounts/out-of-range scores/cross-field tampering all fail) before being considered done — not just syntax-checked. Also added defense-in-depth client-side double-submit guards (`nukeProfile`/`cureDamage` share one `_spendingCoins` flag since both draw from the same balance; `watchRewardedAd` gets its own) against the same double-tap race class fixed earlier for `submitRating` — a rapid double-tap could otherwise let two overlapping calls both pass a synchronous balance check against the same stale balance. 3 new regression tests in `xp_progression_integration_test.dart`. **Not fully closed, disclosed rather than silently accepted**: (1) an attacker can still write *many separate, individually-legitimate-shaped* transactions (e.g. `{reason: 'ratingGiven', amount: 2}` repeated in a loop) to slowly accumulate balance, since Firestore rules validate each document in isolation and can't cheaply enforce "only one `dailyChallengeCompleted` reward per challenge per day" the way `ratings`/`choiceVotes` enforce uniqueness via a deterministic doc id — transaction docs use a random UUID with no such constraint. (2) A nuke's coin cost and its score effect are two separate, non-atomic writes (always true, not introduced by this pass) — a client bypassing the app UI could still apply nuke-sized (not arbitrary) damage without paying. (3) `cosmeticPurchases`/`userAchievements` still accept any `cosmeticId`/`achievementId` from a signed-in device without verifying the underlying criteria were actually met — lower severity since neither directly grants coins. Fully closing all three requires moving reward-granting to Cloud-Function-only writes (the client's own action documents trigger the grant server-side, and the client loses write access to `coins`/`xp`/`score`/transaction collections entirely) — a genuine architecture change, flagged to the user rather than silently attempted. **`firestore.rules` changes are written and locally verified but NOT deployed** — deploying to the live project needs explicit confirmation first (a production infrastructure change), per this project's own safety rules. |

Architecture: `RepositoryBundle`/`repositoryBundleProvider` picks `Local*` or `Remote*` for
every repository based on `FirebaseAuth.instance.currentUser` — the switch is transparent to
`AppController` and every screen, since both implementations satisfy the same abstract
interfaces that were already in place before this migration.

## Why the rest isn't "done in one pass"

This spec is ~15 phases covering new models, services, repositories, screens, and a moderation
surface (comments) that touches privacy/safety directly. Building all of it in one sitting without
verification between phases is exactly what the spec's own Section 47 ("Do not move to the next
phase if the current phase is broken") warns against. This document will be updated as each
subsequent phase lands.
